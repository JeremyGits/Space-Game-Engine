🤝 Contributing Guide

How to contribute to the Space Game Engine

Welcome Contributors!

Thank you for your interest in contributing to the Space Game Engine! This guide will help you get started with contributing code, documentation, or other improvements.

Ways to Contribute

  • 🐛 Report bugs and issues
  • 💡 Suggest new features
  • 📝 Improve documentation
  • 🔧 Submit bug fixes
  • ✨ Implement new features
  • 🎨 Create examples and demos
  • 📚 Write tutorials

Getting Started

1. Fork and Clone

# Fork the repository on GitHub, then clone your fork
git clone https://github.com/YOUR_USERNAME/SpaceGame.git
cd SpaceGame

# Add upstream remote
git remote add upstream https://github.com/ORIGINAL_OWNER/SpaceGame.git

2. Install Dependencies

npm install

3. Create a Branch

# Create a branch for your feature or fix
git checkout -b feature/your-feature-name

# Or for bug fixes
git checkout -b fix/bug-description

4. Make Your Changes

Write your code following our coding standards (see below).

5. Test Your Changes

# Run the development server
npm run dev

# Build to check for errors
npm run build

6. Commit Your Changes

# Stage your changes
git add .

# Commit with a descriptive message
git commit -m "feat: add new feature description"

# Or for bug fixes
git commit -m "fix: resolve issue with X"

7. Push and Create Pull Request

# Push to your fork
git push origin feature/your-feature-name

# Then create a Pull Request on GitHub

Coding Standards

TypeScript Style Guide

Naming Conventions

// Classes: PascalCase
class GameEngine { }
class FirstPersonController { }

// Interfaces: PascalCase with 'I' prefix (optional)
interface EntityConfig { }
interface IComponent { }

// Functions and variables: camelCase
function updatePlayer() { }
const playerPosition = new Vector3();

// Constants: UPPER_SNAKE_CASE
const MAX_ENTITIES = 1000;
const DEFAULT_SPEED = 5.0;

// Private members: prefix with underscore
class Example {
  private _privateField: number;
  private _privateMethod(): void { }
}

File Organization

  • One class per file
  • File name matches class name
  • Use index.ts for barrel exports
  • Group related files in directories
// Good
src/engine/core/Entity.ts
src/engine/core/Component.ts
src/engine/core/index.ts  // Exports Entity, Component, etc.

// Bad
src/engine/core/AllClasses.ts  // Multiple classes in one file

Code Formatting

  • Use 2 spaces for indentation
  • Use single quotes for strings
  • Add semicolons
  • Max line length: 100 characters
  • Use trailing commas in multi-line objects/arrays

Documentation

/**
 * Brief description of the class/function
 * 
 * @param paramName - Description of parameter
 * @returns Description of return value
 * @example
 * ```typescript
 * const example = new Example();
 * example.doSomething();
 * ```
 */
class Example {
  /**
   * Method description
   */
  doSomething(): void {
    // Implementation
  }
}

Commit Message Guidelines

We follow the Conventional Commits specification:

type(scope): subject

body (optional)

footer (optional)

Types

  • feat: New feature
  • fix: Bug fix
  • docs: Documentation changes
  • style: Code style changes (formatting, etc.)
  • refactor: Code refactoring
  • perf: Performance improvements
  • test: Adding or updating tests
  • chore: Maintenance tasks

Examples

# Feature
feat(input): add gamepad vibration support

# Bug fix
fix(physics): resolve collision detection issue on slopes

# Documentation
docs(api): update FirstPersonController documentation

# Refactoring
refactor(rendering): optimize material system performance

# Breaking change
feat(core)!: redesign entity component system

BREAKING CHANGE: Entity API has changed, see migration guide

Pull Request Process

Before Submitting

  • ✅ Code follows the style guide
  • ✅ All tests pass
  • ✅ Documentation is updated
  • ✅ Commit messages follow guidelines
  • ✅ Branch is up to date with main

PR Template

## Description
Brief description of changes

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change
- [ ] Documentation update

## Testing
How has this been tested?

## Checklist
- [ ] Code follows style guidelines
- [ ] Self-review completed
- [ ] Documentation updated
- [ ] No new warnings
- [ ] Tests added/updated

Review Process

  1. Submit pull request
  2. Automated checks run (build, lint)
  3. Code review by maintainers
  4. Address feedback
  5. Approval and merge

├── src/
│   ├── engine/          # Core engine code
│   │   ├── core/        # ECS, game loop, scene management
│   │   ├── rendering/   # Rendering systems
│   │   ├── physics/     # Physics systems
│   │   ├── input/       # Input handling
│   │   └── player/      # Player controllers
│   ├── game/            # Game-specific code
│   ├── components/      # React components
│   ├── hooks/           # Custom React hooks
│   ├── store/           # State management
│   ├── utils/           # Utility functions
│   └── types/           # TypeScript type definitions
├── docs/                # Documentation
├── public/              # Static assets
└── tests/               # Test files

Where to Add Code

  • Engine features → src/engine/
  • Game logic → src/game/
  • UI components → src/components/
  • Utilities → src/utils/
  • Type definitions → src/types/

Testing Guidelines

Manual Testing

  1. Run npm run dev
  2. Test your changes in the browser
  3. Check console for errors
  4. Test on different browsers if possible
  5. Test with gamepad if input-related

Performance Testing

  • Check FPS counter
  • Monitor memory usage
  • Profile with browser DevTools
  • Test with large object counts

Documentation

Code Documentation

  • Add JSDoc comments to public APIs
  • Include usage examples
  • Document parameters and return values
  • Explain complex algorithms

Documentation Site

Documentation is in docs/ directory:

  • docs/pages/getting-started/ - Tutorials
  • docs/pages/engine/ - Engine documentation
  • docs/pages/api/ - API reference
  • docs/pages/development/ - Development guides

Adding Documentation

  1. Create HTML file in appropriate directory
  2. Follow existing page structure
  3. Use dark theme styling
  4. Add navigation links
  5. Include code examples

Best Practices

Code Quality

  • Write clean, readable code
  • Keep functions small and focused
  • Avoid premature optimization
  • Use meaningful variable names
  • Comment complex logic

Performance

  • Profile before optimizing
  • Use object pooling for frequent allocations
  • Avoid creating objects in game loop
  • Use GPU instancing for many objects
  • Implement LOD for complex scenes

Architecture

  • Follow ECS patterns
  • Keep components as data containers
  • Put logic in systems
  • Use events for loose coupling
  • Separate engine from game code
